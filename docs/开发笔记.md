## macOS 上怎么给自己的窗口截图

调试界面时最费时间的一步。**结论先行：只有下面这一招稳定可用。**

```python
import Quartz
from AppKit import NSBitmapImageRep
from io import BytesIO
from PIL import Image

img = Quartz.CGWindowListCreateImage(
    Quartz.CGRectNull,                                  # 不是 CGRectMakeNullRect
    Quartz.kCGWindowListOptionIncludingWindow,         # = 8
    window_id,                                          # 从 CGWindowListCopyWindowInfo 拿
    Quartz.kCGWindowImageBoundsIgnoreFraming)           # = 1，不是 kCGWindowImageBoundsOnly
rep = NSBitmapImageRep.alloc().initWithCGImage_(img)
data = rep.representationUsingType_properties_(4, {})   # 4 = PNG
pil = Image.open(BytesIO(data)).convert("RGB")
```

### 哪些方式不管用（都试过）

| 方式 | 结果 |
|------|------|
| `screencapture -R x,y,w,h` | 抓到壁纸或别的窗口。窗口坐标对不上，且无边框置顶窗口（layer 19）不在截图合成里 |
| `screencapture -l <window_id>` | `could not create image from window` |
| `PIL.ImageGrab.grab(bbox=...)` | 同 `-R`，抓到遮挡物 |
| `Quartz.CGWindowListCreateImage` + `CGRectMakeNullRect` | `ImportError` — pyobjc 里叫 `CGRectNull` |
| `CIContext().createCGImage(img, None)` | `AttributeError` — 新版 pyobjc 没这方法，直接把 CGImage 喂给 `NSBitmapImageRep` |

### 其他坑

- **必须在 Tk 事件循环里截图**：`root.after(...)` 回调里调，窗口才真正上屏。
  窗口刚 `withdraw()` 就抓 → 窗口列表里根本没有它。
- **按 PID 过滤**：`w.get('kCGWindowOwnerPID') == os.getpid()`，
  比按 owner name 过滤可靠（多个 `python3` 进程会混淆）。
- **PyInstaller 打包后的 app 仍取不到**：`CGWindowListCreateImage` 返回
  `NSInternalInconsistencyException - cgImage != NULL`。
  验证打包产物时，改跑同一份源码来截图（代码相同，视觉一致）。
- **venv 里跑 tkinter 会缺 Tcl**：`Cannot find a usable init.tcl`。
  用 managed python（`/Users/zhounanxi/.workbuddy/binaries/python/versions/3.13.12/bin/python3`），
  额外依赖用 `PYTHONPATH` 指向另一个 venv 的 site-packages。

## CustomTkinter 混排的坑

### 1. CTkEntry 的 width 单位是像素，不是字符数

```python
# ❌ 「120」会被截成「12C」——末位直接看不见
ctk.CTkEntry(self, width=4 * 9)

# ✅ 按像素给足
ctk.CTkEntry(self, width=56)
```

纯看代码发现不了，得截图。判断够不够宽：

```python
needed = tkinter.font.Font(root=root, font=entry.cget("font")).measure("120")
actual = max(entry.winfo_width(), entry.winfo_reqwidth())
```

（`winfo_width()` 在控件未映射时返回 1，要和 `winfo_reqwidth()` 取 max。）

### 2. 别用 `self.attr = None` 当「类型标记」

```python
# ❌ hasattr(x, "var_m") 依然返回 True
self.var_m = None

# ❌ 后果：按 hasattr 分派逻辑的代码会把数字拨轮当成时间拨轮
if hasattr(w, "var_m"):
    w.var_h.set(...)      # AttributeError
```

用 `isinstance` 或直接设一个**真正不存在的属性名**来区分类型。

### 3. CTK 控件不要和原生 tk 控件共用一棵控件树

CTK 的 `configure()` 会遍历 `winfo_children()`，碰到已销毁的控件会抛
`TclError: bad window path name`。

- **生产环境通常没事**：面板是独立 Toplevel，关掉时整棵树一起销毁。
- **测试里会崩**：跨用例复用同一个 `tk.Tk()` root 时，
  上一个用例销毁的 CTK 控件会残留。

解法：测试里给 CTK 单独开一个 `tk.Tk()`：

```python
ctk_root = tk.Tk(); ctk_root.withdraw()
try:
    dlg = hf.SettingsDialog(ctk_root, cfg)
    ...
finally:
    ctk_root.destroy()
```

### 4. 别单独 destroy CTK 控件

同理会触发上面的遍历崩溃。统一在 root 层面清理。

## PyInstaller 打包可选依赖

`customtkinter` 是可选依赖（有就新版面板，没有就降级到原生 tk 面板）。
两个必须做对的地方：

**1. `--collect-all` 只能在模块真的装了时才加**

```bash
CTK_ARGS=()
if [ "$HAVE_CTK" = "1" ]; then
    CTK_ARGS=(--collect-all customtkinter)
fi
"$BUILD_PY" -m PyInstaller ... "${CTK_ARGS[@]}" ...
```

PyInstaller 遇到不存在的模块会**直接报错中止**，不是警告。
CTK 带主题 JSON（`assets/themes/*.json`）和字体（Roboto ttf、shapes.otf），
不 collect 的话运行时找不到，界面会崩。

**2. 构建脚本要自动装**

构建机的 Python 未必有 CTK（本项目就踩到：只有 venv 里有，
`python3`/`/usr/bin/python3` 都没有，结果打出来的包没有 CTK 资源）。
构建前主动 `pip install customtkinter` 并检测，失败则降级出包。

**验证包内有没有：**

```bash
find "dist/Health Float.app" -path "*customtkinter*" -name "*.json"
find "dist/Health Float.app" \( -name "*.otf" -o -name "*.ttf" \)
```

体积会明显变化（本项目 69M → 79M）。

## 两个「本地好、CI 挂」的经典陷阱

这两个都差点漏到线上，而且都**只有一套平台组合会暴露**——
本地跑通了不代表没问题。

### 1. `time.monotonic()` 没有统一的起点

同一台 Mac 上实测：

| Python | `time.monotonic()` 返回 |
|--------|----------------------|
| 3.9.6 | **0.08s**（进程启动以来的时长）|
| 3.13.12 | **104472s**（系统运行时长）|

所以**绝不能用 `0.0` 当「某件事还没发生过」的哨兵**：

```python
# ❌ 在 3.9 上：now - 0.0 = 0.08 < 1.5 → 第一次就被节流吞掉
self._last_extend = 0.0
if now - self._last_extend < 1.5:
    return False

# ✅ 用 None 表达「没有上次记录」，与时钟基准无关
self._last_extend = None
if (self._last_extend is not None
        and now - self._last_extend < 1.5):
    return False
```

**排查手法**：在测试里把 `time.monotonic` 换成返回接近 0 的假函数，
一次跑完整套件就能把所有依赖时钟基准的代码揪出来：

```python
_base = {"t": 0.02}
def small_monotonic():
    _base["t"] += 0.0005
    return _base["t"]
time.monotonic = small_monotonic
```

（同类问题：`time.perf_counter()` 在 3.9 上也是进程相对。
`datetime.now()` 是墙钟，跨平台一致，可放心用。）

### 2. 中文日志在 Windows 控制台上会抛异常

Windows 控制台默认 **cp1252**，写不下中文 → `UnicodeEncodeError`。

要命的是本项目的日志**几乎都在 `except` 分支里**，
本该「优雅降级」的路径会因为打印错误信息而二次崩溃：

```python
# 配置文件损坏 → 本该回退默认配置
except Exception as e:
    print(f"[health-float] 配置读取失败，使用默认配置: {e}")   # ← 这里炸了
```

**解法：日志永远不能影响主流程。**

```python
def _log(msg):
    try:
        print(msg)
    except UnicodeEncodeError:
        try:
            enc = sys.stdout.encoding or "ascii"
            print(msg.encode(enc, errors="replace").decode(enc, errors="replace"))
        except Exception:
            pass
    except Exception:
        pass
```

**测试里怎么模拟：** 换掉 `sys.stdout`，让它在写不下时抛异常——
和真实 Windows 控制台行为一致：

```python
class AsciiConsole:
    encoding = "cp1252"
    def write(self, text):
        text.encode(self.encoding)   # 写不下就抛
        return len(text)
    def flush(self):
        pass
```

### 3. `tk_popup()` 在无人值守环境会阻塞

`menu.tk_popup()` 会进入 Tk 的事件循环等用户点击。CI 上没人点，
就阻塞到超时（本项目：本地 30 秒，CI 上 **20 分钟**）。

**解法：把「构建菜单」和「弹出菜单」分开。**

```python
def _build_menu(self):
    menu = tk.Menu(self.root, tearoff=0)
    menu.add_command(label="⚙  打开设置…", command=self._open_settings)
    return menu

def _show_menu(self, e):
    menu = self._build_menu()
    try:
        menu.tk_popup(e.x_root, e.y_root)
    finally:
        menu.grab_release()
```

测试只调 `_build_menu()` 检查菜单项，不触发弹出。
整套测试耗时从 1201s 降到 1.1s。

**通用原则**：任何会进入 GUI 事件循环的调用（`tk_popup`、`mainloop`、
`wait_window`）都不该出现在单元测试里。

## macOS 会偷偷把无边框窗口变回标准窗口

浮窗偶尔会「变回」带标题栏、红绿灯、可拖拽缩放的普通窗口
（用户 2026-11-12 截图反馈）。

### 三个反直觉的点

**1. 重置后 `overrideredirect()` 返回 `None`，不是 `False`**

```python
root.overrideredirect(False)
root.update()
print(root.overrideredirect())    # → None（不是 False！）
```

所以判断要写成「不是 True」：

```python
if root.overrideredirect() is not True:
    root.overrideredirect(True)
```

**2. 启动时兜底几次是不够的**

原来的写法只有 `<Map>` 绑定 + `after(200)` + `after(1200)`。
实测重置发生在启动**之后**，那之后没有任何机制会修它 ——
窗口就带着标题栏一直留到下次启动。

正确做法是**持续巡检**：

```python
def _borderless_watch(self):
    self._ensure_borderless()
    try:
        self.root.after(2000, self._borderless_watch)   # 自我续期
    except tk.TclError:
        pass
```

2 秒一次足够 —— 标题栏的视觉损伤远小于 2 秒，
而 `overrideredirect()` 是 Tcl 调用，别放到每帧动画里。

**3. 三重保险各有分工，别只留一层**

| 机制 | 覆盖的场景 |
|------|-----------|
| `<Map>` 绑定 | 窗口被重映射的瞬间，立刻修复（无延迟）|
| 启动后两次 after | 启动竞态（窗口刚建好时的样式抖动）|
| 2 秒巡检 | 运行中任何时刻的静默重置 |

### 怎么测

把判断逻辑抽成纯函数，才能脱离 GUI 时序测：

```python
def _needs_borderless_fix(state):
    return state is not True
```

**踩过的坑**：一开始的测试写成「先 `overrideredirect(False)` 重置，
再断言修复后是 True」。单独跑通过，全套跑就挂 ——
因为**前一个用例注册的巡检已经把窗口修好了**，重置根本没发生。
改成测纯函数的三种分支 + 端到端真实重置，顺序依赖就消失了。

### 诊断小技巧

判断窗口是不是无边框，看 Quartz 里的窗口层：

```python
import Quartz
for w in Quartz.CGWindowListCopyWindowInfo(
        Quartz.kCGWindowListOptionAll, Quartz.kCGNullWindowID):
    b = dict(w.get('kCGWindowBounds', {}))
    print(w.get('kCGWindowLayer'), b.get('Width'), b.get('Height'))
```

- `layer=19` → 无边框浮窗（正常）
- `layer=0` → 普通窗口（带标题栏，出问题了）

用户截图也可以这样量化：截图的像素尺寸 ÷ 2 = 逻辑尺寸。
标题栏占 48 物理像素 = 24 逻辑像素，一量就知道多出了标题栏。

## macOS Tk 会静默忽略映射前的窗口位置

浮窗该在屏幕右下角，实际却停在 **(5,30)** —— 那是 Tk 的默认层叠位置。
一眼就看出「位置设置根本没生效」。

### 机制

macOS 上 Tk 的 `geometry()` 里，**位置参数在窗口映射（显示）之前会被静默忽略**，
不报错、不警告。实测：

```python
r = tk.Tk()
r.overrideredirect(True)
r.geometry("140x241+1240+610")     # ← 位置被忽略
r.update()
print(r.winfo_x(), r.winfo_y())    # → 5 30
```

窗口显示之后再设一次就生效：

```python
r.geometry("140x241")
r.update()                          # 先让窗口映射出来
r.geometry("+1240+610")             # 再设位置 → 1240 610 ✅
```

`withdraw()` → `deiconify()` 的往返同理。

### 修法

```python
def _place_at_default(self):
    if self.root.winfo_viewable():
        self.root.geometry(f"+{self.x}+{self.y}")
```

启动后 `root.after(120, self._place_at_default)` 调一次。

**注意**：`root.after(0, ...)` 太早（还是映射前），120ms 是实测够用的值。

### 为什么这个坑特别难发现

它**不报错**，而且 5,30 这个位置看起来「也挺合理」（左上角），
不像崩溃那么显眼。窗口显示出来后你会以为它就长那样。

只有当你**主动测量** `winfo_x()/winfo_y()` 并和预期值对比时才会暴露。
所以：改了窗口相关的代码，就把坐标断言写进测试里。

### 顺带一提

判断窗口状态时，Quartz 的 `kCGWindowLayer` 很直观：

| layer | 含义 |
|-------|------|
| 19 | 无边框浮窗（正常）|
| 0 | 普通窗口（带标题栏）|

`onscreen=None` 的那些是 Tk 的隐藏辅助窗口，不可见，不用管。

## 发布出去的东西，和你以为发布出去的不是一回事（15:00 → 17:30）

这一节记的不是代码问题，是**审计发布产物时挖出的三个静默缺陷**。
它们的共同点：不报错、不崩溃、CI 全绿，只有把「实际产物」和
「代码里声称的样子」逐项对起来，才会暴露。

### 缺陷 1：发出去的 DMG 是 arm64-only，README 却承诺通用

README 写「macOS（Intel + Apple Silicon 通用）」。但用户下载到的 DMG：

```
$ lipo -info "Health Float.app/Contents/MacOS/Health Float"
Non-fat file: ... is architecture: arm64
```

**Intel Mac 用户根本装不了**。原因是我在本机构建时用的是单架构
Python（Homebrew / managed 版本），而 `build_macos_app.sh` 里那段
「只有构建器本身是 universal2 时才敢这么做」的判断是对的 ——
它只是老实降级成单架构，而我没注意到降级结果被发了出去。

反倒是 **CI 那边是对的**：release.yml 装 python.org 官方版 Python
（自带 universal2），实测 CI 产物：

```
Architectures in the fat file: ... are: x86_64 arm64
```

但它被一个 flag 挡在门外：

```yaml
overwrite_files: false   # 「保留手工上传的 universal2 DMG」
```

**当初设这个 flag 的理由已经反转了** —— 想保留的那个「universal2
手工包」，恰恰是后来被单架构包覆盖掉的那个；CI 的 universal2 反而
被挡在了外面。

> **教训**：设 `overwrite_files: false` 这种「保护性」配置时，
> 要写清楚**保护的是哪个具体产物**。当时写「保留 universal2 DMG」，
> 三周后手工上传的 DMG 变成了 arm64-only，注释和现实完全对不上，
> 而 CI 里躺着真正的 universal2 包没人用。
>
> 另外：**arch 承诺必须验**，不能只靠 `lipo -info` 打印一行就发布 ——
> 那行日志不会让 CI 失败。

### 缺陷 2：Windows / Linux 资产停留在三周前

`HealthFloat-Windows.zip` 里数 customtkinter 文件：

```
$ unzip -l w.zip | grep -ci customtkinter
0
```

整个包零个 CTK 文件 —— 没有现代圆角设置面板，
黑屏延长修复、无边框巡检、窗口位置修复**全都没进去**。
AppImage 同理。

根因还是上面那个 flag：CI 明明构建了新包，
`overwrite_files: false` 让它**只填补缺失的平台，不更新已存在的**。
于是 macOS 靠手工上传更新了，Windows/Linux 永远停在 11-10。

### 缺陷 3：Windows 的 zip 把自己包进去了

```
$ unzip -l w.zip | grep -i zip
    43  11-10-2026 09:09   HealthFloat-Windows.zip   <-- 43 字节空壳
```

`shutil.make_archive('dist/X','zip','dist')` 的 root_dir 就是
zip 的**输出目录** —— 边写边扫，把半成品自己扫进去了。
用户解压会看到一个 43 字节的空 zip，还以为下载坏了。

正确写法是限定只扫子目录：

```python
shutil.make_archive('dist/X', 'zip', root_dir='dist', base_dir='Health Float')
```

### 顺带：GitHub 会把资产名里的空格换成点

发布脚本产出的是 `Health Float.dmg`，但 GitHub 上实际是
`Health.Float.dmg`。机制在 `softprops/action-gh-release`：

```ts
export const alignAssetName = (assetName: string): string =>
  assetName.replace(/ /g, '.');
```

所以 **README 和 Release 正文里必须写点号版**，写空格版用户按文档
去找文件会找不到。已发布的 v1.2.0 正文里写的就是空格版。

### 副作用：CTK 主题 JSON 到底要不要 --collect-all？

一开始以为**必须加**——CTK 的主题是 JSON 数据文件，
PyInstaller 静态分析不收 JSON，缺了会崩。

实测才发现 PyInstaller 自带 `hook-customtkinter.py`：

```python
datas = collect_data_files("customtkinter")
```

**数据文件它早就收了**。跑了一个探针包验证：没加
`--collect-all` 的产物照样 `WIDGETS OK`，主题正常加载。

所以 `--collect-all` 的真实价值是三点：
1. 额外收 hiddenimports 和 binaries，比只收 datas 更保险；
2. **和其他四个打包脚本口径一致**（这才是改它的主要理由）；
3. 显式优于隐式 —— 依赖上游 hook 的行为，早晚会被上游改掉。

### 方法论：把「声称」和「实际」逐项对起来

这次的三个缺陷，本地全绿、CI 全绿、代码读起来完全正常。
是下面这张表把它抓出来的：

| 声称 | 实际 | 怎么发现的 |
|---|---|---|
| README：Intel + Apple Silicon 通用 | `lipo` → arm64 only | 挂载 DMG 查架构 |
| CI 产物是最新的 | zip 里 CTK 计数 = 0 | 下载资产逐项检查 |
| zip 是完整的包 | 里面有个 43 字节空壳 | `unzip -l` 看清单 |

**审计发布产物 = 把 README 的每句承诺，对着实际文件验一遍。**
光看 CI 绿不绿是不够的 —— CI 绿只说明「脚本跑完了」，
不说明「发出去的东西对」。

### 新增：tests/test_packaging.py

### 插曲：加 `--collect-all customtkinter` 引发的 universal2 构建失败

修完上面三个缺陷后重新跑 Release，**macOS job 当场挂了**：

```
IncompatibleBinaryArchError:
  PIL/_avif.cpython-312-darwin.so is not a fat binary!
```

这是我上一步引入的。链条是：

```
--collect-all customtkinter
  → CTK 的 ctk_image.py 里 `from PIL import Image, ImageTk`
  → PyInstaller 把整个 Pillow 拖进包里
  → Pillow 的编译扩展（_avif.so 等）是**单架构**二进制
  → universal2 构建要把它转成双架构 → 报错
```

验证 Pillow 扩展确实是单架构：

```
$ lipo -info .../PIL/_avif.cpython-313-darwin.so
Non-fat file: ... is architecture: arm64
```

**修法：所有打包脚本都加 `--exclude-module PIL`。**

为什么能排除：本项目图片一律用 `tk.PhotoImage` 读 PNG，
`health_float.py` 完全不 import PIL。而 CTK 那边的 PIL 是
`try: from PIL import Image, ImageTk / except ImportError: pass`
包的**软依赖**，排除后照常工作 —— 实测排除 PIL 的探针包
仍然 `WIDGETS OK`，主题正常加载。

顺带发现：图标生成那段也依赖 Pillow，但
`assets/app-icon.png` 已经在仓库里，那条分支**根本不会执行**。
顺手把它改清楚：图标缺失时明确报错并提示装 Pillow 或补图，
而不是静默跳过（原来 `raise SystemExit(0)` 会让构建继续，
然后在后面某处莫名其妙地失败）。

> **教训**：**软依赖会顺着 import 链偷偷变成硬依赖。**
> CTK 声明 PIL 是可选的，但 `--collect-all` 把它变成必收，
> 于是「可选依赖」在打包层面变成了「必须能转架构的依赖」。
>
> 排查这类问题的通用手法：**看报错里那个意外的包是谁带进来的**。
> `_avif.so` 不是我直接装的 Pillow 吗 —— 对，但它是被 CTK 拖进来的。
>
> 另外：universal2 构建会**放大**单架构依赖的问题。
> 单架构构建时单架构的 .so 完全没问题，一到 universal2 就炸。
> 所以**双架构构建是依赖卫生的照妖镜**。
