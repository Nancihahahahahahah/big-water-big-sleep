## macOS 上怎么给自己的窗口截图

调试界面时最费时间的一步。**结论先行：只有下面这一招稳定可用。**

```python
import Quartz
from AppKit import NSBitmapImageRep
from io import BytesIO
from PIL import Image

img = Quartz.CGWindowListCreateImage(
    Quartz.CGRectNull,                                  # 不是 CGRectMakeNullRect
    Quartz.kCGWindowListOptionIncludingWindow,         # = 8
    window_id,                                          # 从 CGWindowListCopyWindowInfo 拿
    Quartz.kCGWindowImageBoundsIgnoreFraming)           # = 1，不是 kCGWindowImageBoundsOnly
rep = NSBitmapImageRep.alloc().initWithCGImage_(img)
data = rep.representationUsingType_properties_(4, {})   # 4 = PNG
pil = Image.open(BytesIO(data)).convert("RGB")
```

### 哪些方式不管用（都试过）

| 方式 | 结果 |
|------|------|
| `screencapture -R x,y,w,h` | 抓到壁纸或别的窗口。窗口坐标对不上，且无边框置顶窗口（layer 19）不在截图合成里 |
| `screencapture -l <window_id>` | `could not create image from window` |
| `PIL.ImageGrab.grab(bbox=...)` | 同 `-R`，抓到遮挡物 |
| `Quartz.CGWindowListCreateImage` + `CGRectMakeNullRect` | `ImportError` — pyobjc 里叫 `CGRectNull` |
| `CIContext().createCGImage(img, None)` | `AttributeError` — 新版 pyobjc 没这方法，直接把 CGImage 喂给 `NSBitmapImageRep` |

### 其他坑

- **必须在 Tk 事件循环里截图**：`root.after(...)` 回调里调，窗口才真正上屏。
  窗口刚 `withdraw()` 就抓 → 窗口列表里根本没有它。
- **按 PID 过滤**：`w.get('kCGWindowOwnerPID') == os.getpid()`，
  比按 owner name 过滤可靠（多个 `python3` 进程会混淆）。
- **PyInstaller 打包后的 app 仍取不到**：`CGWindowListCreateImage` 返回
  `NSInternalInconsistencyException - cgImage != NULL`。
  验证打包产物时，改跑同一份源码来截图（代码相同，视觉一致）。
- **venv 里跑 tkinter 会缺 Tcl**：`Cannot find a usable init.tcl`。
  用 managed python（`/Users/zhounanxi/.workbuddy/binaries/python/versions/3.13.12/bin/python3`），
  额外依赖用 `PYTHONPATH` 指向另一个 venv 的 site-packages。

## CustomTkinter 混排的坑

### 1. CTkEntry 的 width 单位是像素，不是字符数

```python
# ❌ 「120」会被截成「12C」——末位直接看不见
ctk.CTkEntry(self, width=4 * 9)

# ✅ 按像素给足
ctk.CTkEntry(self, width=56)
```

纯看代码发现不了，得截图。判断够不够宽：

```python
needed = tkinter.font.Font(root=root, font=entry.cget("font")).measure("120")
actual = max(entry.winfo_width(), entry.winfo_reqwidth())
```

（`winfo_width()` 在控件未映射时返回 1，要和 `winfo_reqwidth()` 取 max。）

### 2. 别用 `self.attr = None` 当「类型标记」

```python
# ❌ hasattr(x, "var_m") 依然返回 True
self.var_m = None

# ❌ 后果：按 hasattr 分派逻辑的代码会把数字拨轮当成时间拨轮
if hasattr(w, "var_m"):
    w.var_h.set(...)      # AttributeError
```

用 `isinstance` 或直接设一个**真正不存在的属性名**来区分类型。

### 3. CTK 控件不要和原生 tk 控件共用一棵控件树

CTK 的 `configure()` 会遍历 `winfo_children()`，碰到已销毁的控件会抛
`TclError: bad window path name`。

- **生产环境通常没事**：面板是独立 Toplevel，关掉时整棵树一起销毁。
- **测试里会崩**：跨用例复用同一个 `tk.Tk()` root 时，
  上一个用例销毁的 CTK 控件会残留。

解法：测试里给 CTK 单独开一个 `tk.Tk()`：

```python
ctk_root = tk.Tk(); ctk_root.withdraw()
try:
    dlg = hf.SettingsDialog(ctk_root, cfg)
    ...
finally:
    ctk_root.destroy()
```

### 4. 别单独 destroy CTK 控件

同理会触发上面的遍历崩溃。统一在 root 层面清理。

## PyInstaller 打包可选依赖

`customtkinter` 是可选依赖（有就新版面板，没有就降级到原生 tk 面板）。
两个必须做对的地方：

**1. `--collect-all` 只能在模块真的装了时才加**

```bash
CTK_ARGS=()
if [ "$HAVE_CTK" = "1" ]; then
    CTK_ARGS=(--collect-all customtkinter)
fi
"$BUILD_PY" -m PyInstaller ... "${CTK_ARGS[@]}" ...
```

PyInstaller 遇到不存在的模块会**直接报错中止**，不是警告。
CTK 带主题 JSON（`assets/themes/*.json`）和字体（Roboto ttf、shapes.otf），
不 collect 的话运行时找不到，界面会崩。

**2. 构建脚本要自动装**

构建机的 Python 未必有 CTK（本项目就踩到：只有 venv 里有，
`python3`/`/usr/bin/python3` 都没有，结果打出来的包没有 CTK 资源）。
构建前主动 `pip install customtkinter` 并检测，失败则降级出包。

**验证包内有没有：**

```bash
find "dist/Health Float.app" -path "*customtkinter*" -name "*.json"
find "dist/Health Float.app" \( -name "*.otf" -o -name "*.ttf" \)
```

体积会明显变化（本项目 69M → 79M）。

## CI 里的坑

### Ubuntu runner 已不提供 Python 3.9

`ubuntu-latest` 升级到 26.04 后，`setup-python` 找不到 3.9 构建：

```
The version '3.9' with architecture 'x64' was not found for Ubuntu 26.04
```

用矩阵 `exclude` 把 3.9 从 Ubuntu 那条腿剔掉，3.9 兼容性由 macOS/Windows 覆盖。

### Linux 需要 xvfb

```bash
sudo apt-get install -y xvfb libtk8.6 libtcl8.6
xvfb-run -a python -m unittest discover -s tests -v
```

建窗口必须有 X server，所以连「import tkinter 能过」都不够，
得在 xvfb 下真的 `Tk()` 建一次。

### 免费账号 runner 配额

连续触发多个 run 会排队很久。取消旧 run 释放配额：

```bash
for r in $(gh run list --limit 8 --json databaseId,status -q '.[].databaseId'); do
  gh run cancel $r
done
```

## 两个「本地好、CI 挂」的经典陷阱

这两个都差点漏到线上，而且都**只有一套平台组合会暴露**——
本地跑通了不代表没问题。

### 1. `time.monotonic()` 没有统一的起点

同一台 Mac 上实测：

| Python | `time.monotonic()` 返回 |
|--------|----------------------|
| 3.9.6 | **0.08s**（进程启动以来的时长）|
| 3.13.12 | **104472s**（系统运行时长）|

所以**绝不能用 `0.0` 当「某件事还没发生过」的哨兵**：

```python
# ❌ 在 3.9 上：now - 0.0 = 0.08 < 1.5 → 第一次就被节流吞掉
self._last_extend = 0.0
if now - self._last_extend < 1.5:
    return False

# ✅ 用 None 表达「没有上次记录」，与时钟基准无关
self._last_extend = None
if (self._last_extend is not None
        and now - self._last_extend < 1.5):
    return False
```

**排查手法**：在测试里把 `time.monotonic` 换成返回接近 0 的假函数，
一次跑完整套件就能把所有依赖时钟基准的代码揪出来：

```python
_base = {"t": 0.02}
def small_monotonic():
    _base["t"] += 0.0005
    return _base["t"]
time.monotonic = small_monotonic
```

（同类问题：`time.perf_counter()` 在 3.9 上也是进程相对。
`datetime.now()` 是墙钟，跨平台一致，可放心用。）

### 2. 中文日志在 Windows 控制台上会抛异常

Windows 控制台默认 **cp1252**，写不下中文 → `UnicodeEncodeError`。

要命的是本项目的日志**几乎都在 `except` 分支里**，
本该「优雅降级」的路径会因为打印错误信息而二次崩溃：

```python
# 配置文件损坏 → 本该回退默认配置
except Exception as e:
    print(f"[health-float] 配置读取失败，使用默认配置: {e}")   # ← 这里炸了
```

**解法：日志永远不能影响主流程。**

```python
def _log(msg):
    try:
        print(msg)
    except UnicodeEncodeError:
        try:
            enc = sys.stdout.encoding or "ascii"
            print(msg.encode(enc, errors="replace").decode(enc, errors="replace"))
        except Exception:
            pass
    except Exception:
        pass
```

**测试里怎么模拟：** 换掉 `sys.stdout`，让它在写不下时抛异常——
和真实 Windows 控制台行为一致：

```python
class AsciiConsole:
    encoding = "cp1252"
    def write(self, text):
        text.encode(self.encoding)   # 写不下就抛
        return len(text)
    def flush(self):
        pass
```

### 3. `tk_popup()` 在无人值守环境会阻塞

`menu.tk_popup()` 会进入 Tk 的事件循环等用户点击。CI 上没人点，
就阻塞到超时（本项目：本地 30 秒，CI 上 **20 分钟**）。

**解法：把「构建菜单」和「弹出菜单」分开。**

```python
def _build_menu(self):
    menu = tk.Menu(self.root, tearoff=0)
    menu.add_command(label="⚙  打开设置…", command=self._open_settings)
    return menu

def _show_menu(self, e):
    menu = self._build_menu()
    try:
        menu.tk_popup(e.x_root, e.y_root)
    finally:
        menu.grab_release()
```

测试只调 `_build_menu()` 检查菜单项，不触发弹出。
整套测试耗时从 1201s 降到 1.1s。

**通用原则**：任何会进入 GUI 事件循环的调用（`tk_popup`、`mainloop`、
`wait_window`）都不该出现在单元测试里。
